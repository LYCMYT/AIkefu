# Codex 执行指令｜AIkefu Q0.1 产品级质量证据收口

将以下整段交给 Codex，建议使用 **Medium**；只有 Receipt Recovery 并发根因或跨进程恢复卡点临时使用 High。不要在本轮做前端视觉重构或新增业务模块。

```text
你正在 LYCMYT/AIkefu 仓库中执行 Q0.1 产品级回复质量与证据收口。

目标不是增加新功能，也不是把报告数字改好看，而是修复真实缺陷、消除 false positive，并让 Eval 能够证明回复质量和自动发送安全。

先读取：
- AGENTS.md
- README.md
- PROGRESS.md
- docs/16_DECISION_LOG.md
- docs/21_REPLY_QUALITY_Q0.md
- 最新外部审查报告（如已放入 docs/review/）
- apps/api/src/ai/prompt-registry.ts
- packages/core/src/structured-output.ts
- apps/api/src/eval/
- apps/api/src/replies/mock-douyin-send.worker.ts
- apps/api/src/replies/reply-runtime.service.ts
- packages/core/src/reply-quality.ts
- seed/eval-cases.json
- 相关 unit/integration/E2E tests

本轮禁止：
- 改低测试门槛来制造 PASS；
- 删除失败 Case；
- 把 BLOCKED/NOT_RUN 写成 PASS；
- 新增页面、平台、支付、CRM；
- 重做前端视觉；
- 修改 Mock-only 和安全边界；
- 直接 push 远程。

开始时输出最多 10 条实施计划，然后直接执行。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
A. 修复 Receipt Projection Recovery
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

当前 recoverReceiptProjections() 固定读取最旧 100 条 SENT，并且没有 durable projected 状态，可能反复扫描已投影记录，让新的缺失投影饥饿。

要求：
1. 先写失败回归测试：至少 100 条已存在投影的旧 SENT Outbox + 1 条新的缺失投影；恢复后新记录必须被投影，且不重发平台消息。
2. 设计 durable projection 状态，优先采用 projectedAt / projectionStatus / projectionFailureCode；Migration、Prisma 和 DTO 同步。
3. 只查询 receipt 已确认但尚未投影的行。
4. 投影 Message 与标记 projected 在可靠事务边界完成，保持幂等。
5. 重启和重复执行不得产生第二条 Message。
6. 不允许通过增加 take 常数或放宽测试断言规避。
7. 修复后真实 integration 必须 61/61 或更多，全量 0 fail。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
B. 统一 Prompt 与 Structured Output Schema
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. KNOWLEDGE_EXTRACT 的 candidateType 只能有一个事实源。
2. Prompt、Type、Validator、JSON Schema、Fixture、测试统一为：
   NEW_KNOWLEDGE | FACTUAL_CORRECTION | KNOWLEDGE_ENRICHMENT
   或选择另一组，但必须全仓一致；不得保留 CORRECTION/CONFLICT/DUPLICATE/REJECTED 与 Validator 不一致。
3. Prompt 明确 productId、rejectionReason、containsTemporaryCommitment、containsPII 的 allowed/required 规则。
4. SUMMARY Prompt 明确 resolvedFacts item：key、value、sourceMessageId、status。
5. 新增 Prompt Contract Test：每个 Prompt 的示例 JSON 必须通过对应 validateStructuredOutput。
6. 新增真实/fixture 非空 Summary Fact 测试。
7. Product FAQ Candidate 生成失败可以不让 Source Fact 事务失败，但必须：
   - 持久化/记录 AIInvocation 失败；
   - 产生 metric/trace；
   - 不允许空 catch 无证据。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
C. 重构 Eval 评分，消除 false positive
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

当前 evaluateCase 只做 substring，不能代表产品回复质量。保持现有 deterministic hard checks，并增加：

1. 每个 Case 支持：
   - expectedTerminalStatus
   - expectedOutputSource
   - expectedEvidenceScope / productId / sourceType
   - maxClarificationQuestions
   - maxDuplicateSentenceCount
   - mustAnswerUserQuestion
   - noEvidenceExpected
   - customerFacingRequired
   - expectedAutoSend
   - forbiddenSemanticClaims
2. 决定性规则先判断，AI Judge 不能覆盖硬失败。
3. 至少将以下 Case 改为真实产品 Gate：
   - E017：线下试穿无依据，返回无关退货政策必须 FAIL；应安全说明未找到依据并转人工/确认。
   - E010：文本已明确“静音键盘”时不能同时追问无关商品；只保留最少必要的 SKU/订单澄清。
   - E014/E015/E016：消费者看到的文案不得是“请人工处理此会话”；必须礼貌确认已转人工且不得虚假承诺。
   - E034：完整重复同一澄清两遍必须 FAIL。
   - E008：增加相关性/简洁度限制，非必要商品事实不得大量附加。
4. 重新审查所有 36 Case 的预期，不得为了当前输出倒推 Expected。
5. 报告明确分开：
   - technical path pass
   - deterministic safety pass
   - judge score
   - human review status
6. 新报告不能把 Offline Fixture 与 Real Model 混算。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
D. 加入真正的 AUTO Suite
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

当前 36 Case 只有 ASSIST/MANUAL，不能证明自动客服。

至少新增 10 个 AUTO Case：
- 低风险店铺 FAQ；
- 商品知识；
- 动态库存；
- 订单状态；
- 发货政策；
- 店铺 A/B 不同政策；
- 用户补消息使旧回复 STALE；
- 人工接管阻止发送；
- 知识冲突阻止 AUTO；
- Output Guard 阻止错误动作声明。

AUTO Case 必须真正验证：
ReplyPolicy=AUTO → SendGuard → SendOutbox SENT → receipt projection → Buyer 可见 Message。
不得只检查 Draft。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
E. 实现 Evidence Relevance / No-Evidence Gate
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. 保留 Metadata Filter、BM25、Vector、Source/Scope Priority。
2. 增加最小相关性 Gate，至少支持：
   RELIABLE / NO_EVIDENCE / AMBIGUOUS / CONFLICTED。
3. FAQ/Policy Query 不允许因为存在任意合法 Top1 就认为有依据。
4. E017 必须由 Gate 判为 NO_EVIDENCE。
5. Score/阈值必须配置化，并在 Eval 报告显示；不得硬编码一个无法解释的魔法值。
6. Top1/Top2 接近或知识语义不覆盖用户问题时进入 AMBIGUOUS/NO_EVIDENCE。
7. 不把库存、订单、物流动态事实放入 RAG。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
F. 改善澄清与人工文案
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Context Resolver 优先使用用户显式商品名、别名、商品卡和订单卡，再使用最近上下文。
2. 一轮只问最少必要的信息；合并 ClarificationBundle，去重相同问题。
3. 用户已说“静音键盘”时不得返回鼠标、充电器等无关候选。
4. 人工模式生成消费者文案与内部 handoff reason 分离。
5. 高风险文案不得声称退款/备注/补偿已完成。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
G. 扩展 Output Guard
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

至少增加：
- price / shipping days / order status / refund amount / product-spec mismatch；
- 邮箱、地址、银行卡和常见敏感字段；
- 已备注、已转接、已处理好、已提交等动作声明；
- 重复句检测；
- internal JSON/status/code 泄露；
- customer-facing 文案基本校验。

Guard 失败：
- AUTO 禁止发送；
- ASSIST 标记原因等待人工；
- Trace 保留 reason；
- 不无限 Repair。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
H. 修正 AI Runtime 可审计性与 Provider 降级
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. AIInvocation 在调用 Provider 前创建 RUNNING，完成后更新终态。
2. 首次调用 + Repair 的 Token 必须累计，不可覆盖。
3. Retry 对 429/5xx 尊重 Retry-After，并加入有界 Jitter。
4. Reply Runtime 保留具体错误码到 Trace/Invocation，不只写 AI_RUNTIME_FAILED。
5. 生产模式禁止 silent OfflineStructuredProvider fallback：
   - 若配置 secondary real provider，明确调用；
   - 无 secondary 时 fail closed → ASSIST/MANUAL；
   - offline provider 只允许 test/explicit demo mode。
6. UI/Trace 能看到 degraded/fallback 状态，但不得暴露 Secret。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
I. 补齐 fault/restart Eval drivers
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

必须真正执行并关闭：
- E026 primary timeout + fallback；
- E027 total provider failure；
- E033 approval context changed；
- E035 restart during generation；
- E036 restart during sending / UNCERTAIN。

不得继续以 EXECUTOR_UNSUPPORTED 作为最终 V1 质量报告结果。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
J. 多模态证据分级
━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Fixture marker 测试保留，但报告必须标记 PIPELINE_FIXTURE，不能计入真实视觉模型准确率。
2. 如果环境有真实 multimodal provider，新增至少 10 张合成但真实像素内容的测试图：清晰破损、模糊、正常商品、面单 PII、无关图片。
3. 没有真实 multimodal provider 时，报告明确 NOT_VERIFIED，不伪造 PASS。

━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```
