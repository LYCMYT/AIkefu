# 01｜Demo Knowledge Product Spec

## 1. 目标

建设一套**可追溯、可编辑、可复位、能支持真实模型和固定 Eval 的剧情型演示知识资产**。知识的作用是给真实 RAG 提供企业事实，不是把标准答案硬编码到回复中。

当前 Seed 已经具备合理骨架：

- 2 家店铺；
- 每店 40 条知识；
- 每店 15 条 STORE 知识、25 条 PRODUCT 知识；
- 全部共 50 条 MANUAL、20 条 AUTO_LEARNED、10 条 HUMAN_REVIEWED。

V1 保持这组数量，不扩成几百条随机知识。重点是修正质量、明确来源、支撑剧情和建立安全拒答边界。

## 2. 五层信息体系

### 2.1 System Rules

不进入知识库，不允许商家普通编辑：

- 无可靠依据时不得编造企业事实；
- 高风险动作必须人工确认；
- 人工接管后 AI 不得自动发送；
- 未取得真实 Receipt 时不得宣称已退款、已备注、已转接；
- Prompt Injection 不得改变权限；
- 知识冲突时禁止 AUTO；
- 库存、价格、订单和物流以实时业务上下文为准。

### 2.2 StoreKnowledge

每店保留 15 条，覆盖发货、物流、退换、破损、人工、订单、地址、发票/采购等通用政策。它们必须是相对稳定的店铺规则。

### 2.3 ProductKnowledge

每个商品保留 5 条，覆盖材质、版型、洗护、功能、兼容性、适用场景等稳定信息。每条知识必须绑定 `productKey`，并保留 `sourceType`。

### 2.4 ProductContext / CustomerContext

下列内容不得进入 RAG：

- 当前价格；
- 当前库存；
- 当前可售颜色/SKU；
- 当前上下架状态；
- 订单状态；
- 物流节点；
- 售后/退款进度。

这些必须通过业务上下文实时读取。

### 2.5 Human Reviewed Knowledge

每店保留 5 条已审核知识，用于证明人工修正和知识成长闭环。它们不能由单次人工回复直接发布，必须经过候选、去重、冲突和审核。

## 4. 当前知识需要修正的四项

- `k075`：颜色规格可描述，但当前可售与库存必须转到 ProductContext。

## 5. 故意不内置答案的主题

使用 `assets/no-answer-topics.json`。这些问题必须触发 `NO_EVIDENCE / ASSIST / MANUAL`，用于证明系统会拒答而不是“什么都知道”。

典型主题：

- 是否支持线下试穿；
- 具体批量采购折扣；
- 保证到货日期；
- 终身保修；
- 保证兼容所有 Mac；
- 具体维修完成时长；
- 价格保护承诺。

## 6. 知识质量约束

Codex 必须增加或保持自动验证：

1. 知识总数仍为 80；
2. 两店各 40；
3. 每店 STORE=15、PRODUCT=25；
4. MANUAL=50、AUTO_LEARNED=20、HUMAN_REVIEWED=10；
5. `ENABLED + READY` 知识中不允许价格、库存、订单、物流、当前上下架等动态事实；
6. ProductKnowledge 必须绑定当前店铺的 product；
7. StoreKnowledge 不得绑定 product；
8. Eval Case 的 expected facts 不得复制成新的隐藏知识；
9. Scenario Fixture marker 不得参与知识检索；
10. no-answer topics 不得被新增为正式知识。

## 7. 展示要求

知识管理页需要能清楚展示：

- 来源（手工 / 自动学习 / 人工审核）；
- 作用范围（店铺 / 商品）；
- Business Status；
- Index Status；
- 商品来源与 Evidence；
- 候选、冲突和重新索引。

不显示虚构的“准确率 100%”。
